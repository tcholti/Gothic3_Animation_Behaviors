## Production design review — simplicity / module ownership (2026-11-22)

**Status: HISTORICAL PROPOSAL (superseded by the bounded contract at the end of this task).** This review is read-only for shipping code. It follows project charter `docs/README.md` A0, `ENGINEERING_GUIDE.md` sections 2.1/2.3/4.1/5–7/9/11/13–16, `FEATURE_DEVELOPMENT_METHOD.md` sections 2/5/7–9, `WORK_IMPLEMENTATION_PROTOCOL.md` sections 4–9, and `SOURCE_HOOK_GUIDE.md` sections 3/7–8. EV-458 and EV-459 are factual evidence, not blanket production authorization.

### Target invariant / boundary

When the **factual** CombatMove action is Hack14 and a corresponding Hack Recover asset is positively available, the first Recover primary motion must **not** be native Finishing Recover. The existing later CombatMove routing must still play the correct Hack Recover. If no custom Hack Recover is available, native Recover remains untouched; true Finishing15 is always native. No side effects on other actors/actions, collision, speed, movement, attack continuation or cleanup.

This is an extension of **existing Hack asset routing**, not a new animation state machine, speed/blending correction or general-purpose animation manager.

### Preferred small architecture (conditional on preflight)

1. **Permanent owner:** extend `src/Script_G3AnimationBehaviors/AttackMotionRouting.{h,cpp}` with a narrow decision such as `ShouldSkipNativeFirstRecover(...)` (name illustrative). Reuse the existing factual Action14 and resource-name substitution semantics. The module owns the reason to skip; it does not own hooks, logging or game lifecycle.
2. **Transport only:** `EngineBridge` is the **sole owner** of the physical `Game+0x16E360` StartRecover and `Engine+0x30860` high PlayMotion intercepts if this two-hook approach survives preflight. The former supplies a **synchronous, per-thread/stack-scope** context (SPU, factual Action14, exact actor and Recover boundary); the latter delegates only the **first primary PlayMotion in that context** and either calls the original or skips the single proven wrong invocation. Do not introduce always-on actor tracking, per-frame polling, timers or unrelated state.
3. **Candidate identity:** use Gothic native action/actor/Recover facts first; the pre-play descriptor established in EV-459 is a possible source of the actual first Finishing Recover animation name. Match the **correct generalized native filename contract** (not the probe's exact `Hero_None_2H` string); derive or obtain the corresponding Hack *resource* through the same engine naming/lookup semantics as the existing router. Do **not** infer a universal `.fxm` name by stripping `.xmot` suffixes until the mapping is proved for the relevant asset variants.
4. **Positive fallback gate:** skip the native playback only if the exact corresponding Hack Recover resource can be resolved **before** the wrong PlayMotion. No-resource, unsupported naming, unproven context, missing admin or failed lookup means **call the original native PlayMotion**. No cached success from a different actor/attack/phase.
5. **Production cleanup:** build this into the release target without probe flags. Keep EV-459's hardcoded name, persistent animation-admin pointer, event logs, Tick hooks, diagnostic StopMotion interception and temporary causal policy completely out of production. Do not add an INI switch for correcting existing accepted routing semantics unless a separate user-facing choice is justified.

**Why two potential hooks?** EV-459 showed the first wrong PlayMotion occurs **within** StartRecover, while the existing `Game+0x16B10C` resource query is later and cannot prevent that first playback. One hook can identify the exact factual Recover scope; the second can intercept the wrong PlayMotion. Compare any *proven* narrower single call-site possibility against this, but do not prefer a brittle binary patch solely to reduce hook count. Existing deep/causal diagnostic hooks use the same addresses: production and optional diagnostics must **not** independently install competing physical owners; the bridge should share one transport/observation path or keep incompatible diagnostic configurations mutually exclusive.

### Alternatives, not parallel implementations

- **A — scoped skip (preferred):** EV-459 demonstrated success; minimal new behavior, preserves native lifecycle and later routing. Costs at most one small permanent decision plus a synchronous scope and two native hook boundaries. Remaining risks: safely obtain the current engine animation-admin/resource context; prove the generic filename/resource correspondence; avoid same-address hook conflict.
- **B — substitute Hack on the first native playback:** might also prevent the wrong pose, but would play Hack Recover twice and may change native side effects; not needed by EV-459 and presently **not preferred**.
- **C — rewrite native StartRecover's earlier resource/filename or single-call-site patch:** potentially fewer hooks but requires new precise binary provenance and compatibility proof, may depend on fragile internal offsets; consider only if A cannot meet its gates cleanly. No implementation authority given.
- **D — adjust blend rates / delay motion / generic post-fix pose correction:** treats symptoms, adds unrelated behavior, and is **not warranted**.

### Two evidence gaps before freezing production code

1. **Valid early resource check without stale state.** The probe retained a thread-local `eCAnimationAdmin*` from a *prior* CombatMove resource query. SDK `ge_animationadmin.h` exposes `QueryMotionDataEntity`, but inspected Engine/Script headers did not surface an established public `GetAnimationAdmin` accessor. Research a per-invocation native/SDK way to acquire the correct admin/cache behavior at StartRecover (or a proven, bounded/context-safe alternative). If not established, **stop and return options**; do not convert the probe's borrowed pointer into an unverified permanent cache.
2. **Exact generalized candidate mapping.** Current `AttackMotionRouting` receives a native `.fxm` request and replaces `_FinishingAttack_` with `_HackAttack_` before looking it up. The earlier PlayMotion exposes a `.xmot` descriptor. Prove the common naming relationship for 2H, Staff, relevant directions/variations and applicable modded actors before using the descriptor to construct a candidate. If that contract is not reliable, find the native source that already owns the request name rather than write a filename heuristic.

### Minimal eventual validation (after approved production implementation)

- Positive: visually distinct player 2H Hack, three attacks, no Finishing first playback and direct Hack Recover; genuine knocked-down-opponent Finishing, at least two, remains native.
- Native fallback: no matching custom Hack Recover -> original first native Recover plays; no stuck attack or altered cleanup. Test using an isolated controlled fixture, not an accidental destructive edit of the user's live animation files.
- Generality: tested Staff Hack and additional supported actors/animations as available; unsupported families/other actions unchanged. Cover NPC Hack if factual route is confirmed, not by extrapolation from the player.
- Integration: rapid repetition, Recover interruption, New Balance/AttackCollision compatibility, collision markers/hit counts, speed, movement and bad-block protection remain stable; old production build is the comparison.
- Source/static: one bridge hook owner per RVA, no diagnostic dependency, exactly one conceptual change, native-call parity, no stale pointers; then controlled build/deploy, focused runtime acceptance, and **only afterward** broad production regression.

**Review recommendation:** adopt A as the **working design direction**, but do not freeze or implement production until the two explicit early-availability/naming preflights are resolved and the User reviews the final contract. The objective is a concise invariant enforced at the first authoritative Recover event, not a growing set of exceptional rules.

### Gap A — current engine animation admin / cache behavior: RESOLVED AT API LEVEL

- In the **repository-pinned** SDK `Georgeto/gothic3sdk @ 90bfd344de4510dda7ac9da7461cc7f1eac911f7`, `eCModuleAdmin::GetInstance()` and public `FindModule(bCString const&)` are declared in `g3/Engine/include/g3sdk/Engine/ge_moduleadmin.h`. `eCAnimationAdmin` is an `eCEngineComponentBase` exposing `QueryMotionDataEntity` in `ge_animationadmin.h`. SDK `ge_scriptadmin.cpp` already looks up a module using this same registry; `util/Common/include/g3sdk/util/Util.h` provides a `FindModule<T>` template.
- **Production rule:** obtain the animation admin *at the first Recover decision* with direct `eCModuleAdmin::GetInstance().FindModule("eCAnimationAdmin")` and verify its type (e.g., dynamic_cast); null/wrong type => native original. **Do not use `FindModule<T>()` if it caches a static pointer**, and do not retain the previous resource hook's `eCAnimationAdmin*` across phases/attacks.
- `eEResourceCacheBehavior_Immediate = 1` is the SDK enum value; the tested native CombatMove resource call at `Game+0x16B107` pushes `1`. Use the *same immediate cache behavior* for the early check and reuse `AttackMotionRouting::QueryOptionalSubstitution` rather than introducing another resource-lookup/asset-routing policy.
- Static evidence supports the API; it does **not** yet confirm that this engine instance registers the module under that name in the live game. Verify during focused runtime acceptance. Missing module must fail safe with normal native playback, not crash or suppress.

### Gap B — exact .xmot motion-to-.fxm resource naming: RESOLVED FOR THE DOCUMENTED CONTRACT

- EV-459 observed first native descriptor `Hero_Parade_None_2H_P1_FinishingAttack_Recover_N_Fwd_00_%_00_P0_0.xmot`; the later factual Action14 native request is `Hero_Parade_None_2H_P1_FinishingAttack_Recover_N_Fwd_00_.fxm`, and existing routing selects `Hero_Parade_None_2H_P1_HackAttack_Recover_N_Fwd_00_.fxm`. Deterministic conversion using the `_%_` delimiter reproduced the exact *recorded* native request (local assertion PASS).
- The repository native-name inventory has 5,991 names, including 918 Recover names and **9 Finishing Recover** names (Hero variations, Orc 2H/Staff); all 918 Recover names include `_%_`, and all 9 Finishing Recover names follow `_FinishingAttack_Recover_` and `_%_`. The existing native scheme's P0/P1, actor, equipment and directional prefix is kept unchanged.
- **Production rule:** at the *first* primary PlayMotion under factual Hack14's StartRecover scope, read the incoming descriptor's native motion filename. Require the exact action/phase token `_FinishingAttack_Recover_`, one supported `_%_` variant delimiter and `.xmot` suffix. Construct the native request by keeping the **trailing underscore before** the `%` variant field and appending `.fxm`. Example: `..._Fwd_00_%_00_P0_0.xmot` -> `..._Fwd_00_.fxm` (**not** `..._Fwd_00.fxm`). Call existing `QueryOptionalSubstitution(gEAction_HackAttack, liveAdmin, nativeFxmName, eEResourceCacheBehavior_Immediate)` (illustrative parameter name only); this already replaces the action token and returns a resource only if the corresponding Hack candidate exists. Do **not** duplicate that replacement in a new routing branch.
- Unrecognized filenames/asset conventions, absent custom Hack resource, failure to find the module or a different action/phase => invoke the original native PlayMotion unchanged. This is generalized over *supported naming contracts*, not a claim of universal modded actor compatibility without runtime tests. Recheck Staff and Orc/NPC pathways in acceptance; do not infer support solely from filename inventory.

## Design reopened — custom Hack Hit owns subsequent Recover (User proposal, 2026-11-22)

**Status: ADVISORY ALTERNATIVE; no production implementation authorized.** The User challenged the previous design's "if Hack Recover absent, play native Finishing Recover" fallback: after a genuinely **custom Hack Hit**, they want an absent Hack Recover to follow Gothic's normal no-Recover/idle path, not suddenly animate Finishing Recover. The User reports having tested removed Recover assets causing return to idle. Existing EV-154/EV-161 independently show native *Quick* cleanup can run without Recover asset, but this is not yet proof for the distinct Hack14 resource-return path. The new preference materially changes the prior design's native-fallback requirement; do not automatically implement the previously frozen contract.

**Candidate minimal ownership rule:** factual Hack14 plus evidence that this *execution* actually used unique Hack Hit owns the Recover animation family; native Finishing15 and Hack14 executions which never selected a custom Hack Hit stay as before. EV-458's runtime snapshots show that **all three** Hack14 StartRecover entries still had exact `_HackAttack_Hit_` as active primary motion before original StartRecover stops it. Thus, in the tested fixture, we can potentially derive the necessary fact *at Recover entry* rather than persist a token from the earlier resource hook. This is a candidate simpler than storing cross-phase per-actor state; Staff/NPC/interruptions still need evidence.

**Distinguish two separate native operations:**
1. At `Game+0x16E360`, native StartRecover invokes the **first** primary `Engine+0x30860 PlayMotion` on Finishing Recover (EV-458). EV-459 proved that intercepting and suppressing this single invocation removes the 2H visual glitch; an earlier resource-hook decision alone cannot cancel an independent later PlayMotion without a downstream interception or a proved engine-side control flag. One conceptual feature owner does not imply one physical hook.
2. **Afterward**, the existing `Game+0x16B10C` resource query tries Hack Recover, then explicitly falls back to a Finishing Recover resource if Hack candidate lookup fails. To implement the User's intended no-Hack-Recover semantics, this fallback would need a *narrow owned-case* change. A `nullptr` result here is **not yet proven** equivalent to physically removing an `.xmot`; tested native disassembly at `Game+0x16B112` follows a non-null jump and a different null path with further engine lookup. Do not promise idle without a causal test. Crucially, do not call the original Finishing query for a custom-Hack-Hit-owned missing Recover if the intended contract is no Finishing fallback.

**Comparison / simplest test before changing production:**
- Preferred first candidate: at native StartRecover entry, confirm factual Action14, exact actor, and *currently active custom Hack Hit*. Build one **research-only** scoped guard for the initial Finishing Recover PlayMotion, without requiring Hack Recover existence. Let the later current resource hook check for Hack Recover, but for this exact owned execution **return the engine's missing-resource result** rather than falling back to native Finishing when Hack Recover is absent. This may require carrying only a short-lived execution ownership decision to the later resource lookup; its safe lifetime and cleanup must be examined. Do not add a token unless the outgoing Hack Hit cannot be read reliably or the later lookup needs explicit continuity proof.
- Test A: custom Hack Hit + custom Hack Recover -> initial Finishing suppressed, subsequent Hack Recover plays, no visible leg defect.
- Test B (decisive): custom Hack Hit + **no** custom Hack Recover while native Finishing Recover remains present -> first Finishing suppressed, **no later Finishing**, native gameplay reaches idle/safe completion without stuck action or collision. Test with a reversible, isolated animation fixture, not by modifying User's live originals.
- Test C: factual Hack14 with *no unique Hack Hit* -> preserve native Finishing path. Test D: actual Finishing15 executions stay fully native. Include 2H/Staff and interruptions in later scope after B.
- If the later null-resource path reselects Finishing, fails cleanup, or requires an unproven additional hook, **stop**. Report the narrow alternative (returning native behavior or reusing an existing lifecycle-owned token) to User + Normal Chat; do not grow a workaround/state machine. Existing guardian/C1 opportunity tokens solve different collision-ownership problems and should be reused only if their identity/lifetime truly matches this attack-asset decision.

**Decision gate:** first establish whether a genuinely missing Hack Recover resource in a custom-Hack-Hit-owned execution can naturally end without any Finishing playback. Then freeze whichever bounded design actually satisfies the User's intended behavior. Preserve EV-458/459 and the earlier design as history; `main`, `Backup`, game animation files and release DLL stay untouched throughout read-only design.
