## Current Research Consequence

The B5 parent search remains resolved far enough to reject a misleading interpretation:

> `RunScriptFunction`, `RunScriptState`, and `ProcessScript` are generic script infrastructure, not a central combat-cleanup function.

B6 remains the current runtime gate. EV-176 resolves B6-B far enough for comparison: in three clean 2H Normal completions, the exact outgoing Hit was still observable at StartRecover BEGIN and the captured caller chain was `sAICombatMoveInstr -> ProcessScript()`. The later ordinary native cleanup still occurs after StartRecover returns.

EV-177 confirms the tested legitimate reaction path itself. EV-178 then shows that the first empty-Primary PlayMotion refinement still cannot stack-capture the reaction successor because its Normal attack semantic gate is no longer true by the time the reaction motion is requested. The same run usefully confirms that the gate instead captures fresh Normal Hit installation from empty Primary, and an incidental QuickAttackR interruption shows the same cleanup-to-empty-reaction ordering outside the Normal family.

The next diagnostic question is therefore narrower and more factual:

> Can the existing player/type-0 PlayMotion hook stack-capture every installed successor that begins from an empty Primary during a tightly controlled interruption fixture, without using attack/reaction semantic classification as the capture gate, so the actual Stumble/KnockDown successor stack can be identified post hoc and compared with EV-176?

The lifecycle design hypothesis remains unresolved until that reaction-successor context and the bad direct-replacement context are compared. StartRecover, action/phase, and stale current-movement context remain observations only, not universal lifetime or cleanup authority.
