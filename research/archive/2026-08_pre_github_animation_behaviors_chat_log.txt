This is very useful, and it actually sharpens the architecture we were just converging on.

The animation filename is much less arbitrary than it first appears. The source describes it as a structured encoding of:

Actor family → AniState → Left UseType → Right UseType → Pose → Action → Phase → animation type → Direction → next pose → distance → attack direction.

For example:

Demon_Stand_None_2H_P1_Attack_Hit_N_Fwd_00_%_00_P0_150_L

corresponds roughly to:

Actor=Demon
State=Stand
Left=None
Right=2H
Pose=P1
Action=Attack
Phase=Hit
Type=N
Direction=Fwd
NextPose=P0
Distance=150
AttackDirection=L

That supports our decision to stop treating _Attack_Hit_ as the fundamental way of understanding an animation. Gothic 3 already has the actual semantic values available through gEAction, gEPhase, poses, UseTypes, etc.; the filename is essentially a serialized description of those values.

There is also one especially important detail for our INI design: raw gEUseType does not map one-to-one to the visible animation token. For example, the source says:

gEUseType_Halberd → Staff
gEUseType_Rake → Staff
gEUseType_Shovel → Staff
gEUseType_Axe → 2H
gEUseType_Pickaxe → 2H
gEUseType_PhysicalFist → Fist

and several other raw use types collapse into the same animation category.

That means I would slightly refine what we discussed earlier.

For the user-facing INI, I think the cleanest grouping is probably by the animation UseType category, such as:

None_2H
None_Staff
None_1H
Torch_1H
1H_1H
None_Fist

rather than exposing every raw engine gEUseType.

Internally, the DLL can translate engine UseTypes into the corresponding animation category. So a Halberd naturally resolves to Staff, an Axe to 2H, PhysicalFist to Fist, etc.

That matches how the animation system itself works and keeps the INI much smaller.

For collision, this source reinforces another distinction we've just discovered experimentally. Fist is an animation/use category, and PhysicalFist even maps to the same Fist animation token. That makes it even less likely that the word Fist means a literal physical fist collider. It looks much more like Gothic's generic unarmed/body-combat category, which fits our kick tests and the boar/wolf/golem observations extremely well.

The gEAction and gEPhase sections are also exactly what we want for the next collision revision. Rather than:

filename contains "_Attack_Hit_"

the robust test can become conceptually:

Action = Attack / QuickAttackR / QuickAttackL / ...
and
Phase = Hit
and
exact current motion contains collision marker

The source explicitly defines Hit = gEPhase_Hit = 1, alongside Raise = 0 and Recover = 3.

So our eventual system can be very systematic:

Callback identifies the attack family → gEAction identifies the exact action → gEPhase identifies Raise/Hit/Recover → UseTypes identify the animation/weapon family → marker decides whether that exact animation opts into frame collision.

And the same vocabulary can serve the Raise/speed INI.

I think this information should become part of our permanent design reference because it ties together the three systems—Raise, playback speed, and collision—with Gothic 3's own animation-selection vocabulary rather than something we invented ourselves. 🙂

Good 🙂 Then I’ll treat this as a locked design direction going forward:

use Gothic 3’s own gEAction, gEPhase, pose, and UseType semantics as the primary runtime vocabulary;
use animation filenames mainly as the serialized/selection representation of those values, not as our main parser;
group user-facing INI rules by animation-family categories such as 2H, Staff, 1H, Fist, etc., while translating raw engine UseTypes internally;
keep collision ownership marker-driven per exact animation;
distinguish attack family/action, logical attack source, and physical damage collider as separate concepts.

That should make the collision, Raise, and playback-speed systems fit together much more naturally instead of becoming three separate pieces of logic. 🙂
